## B. CODE DEFECTS STILL OPEN

### B1 — `scripts/10`: `sorted(glob(...))[-1]` is lexicographic last, NOT newest version · OPEN
`find_tte` / `find_rsp` resolve data files this way, commented "newest version". With `.fit`
and `.fit.gz` both present the `.gz` always wins; a directory holding `v00.fit.gz` beside
`v01.fit` would **silently fit the older version** with nothing in the log.
Harmless on this burst (verified byte-identical, sha `e529530479459059`), wrong in general.
**Fix:** parse the `_v(\d+)` token, take the numeric max, prefer the uncompressed copy on a
tie, and record the resolved path in the run's provenance. Lesson D6 in `DataInventory.md`.

### B2 — `scripts/10`: the response-doctrine comment names the wrong threeML version · OPEN
The comment says the rsp2 collapse fallback was deleted because "threeML 2.5.0 count-weights
the response natively". This host runs **2.4.3**, which also count-weights — verified:
`InstrumentResponseSet.from_rsp2_file` + `weight_by_counts` at `time_series_builder.py:257`.
The doctrine holds, the stated version floor is wrong. **Fix:** say ≥2.4.3-verified.

### B3 — `scripts/02_download_data.py` fetches neither `poshist` nor `trigdat` · OPEN
Both were missing for this burst, so detector angles could not be re-derived until I fetched
them by hand. The working downloader already exists at
`scripts/00_prototype_one_burst.py::download_poshist`. **Fix:** call it from `scripts/02`.
Lesson D7 in `DataInventory.md`.

### B4 — `scripts/46_temporal_all106.py` is not bit-reproducible · OPEN
Re-running on unchanged inputs changed `T90_ERR` 0.35319 → 0.35995 (~2%) and moved the lag in
the 8th decimal, although the estimator documents a **deterministic per-trigger seed**. A
stochastic product must reproduce bit-identically on rerun (the seed rule). **Fix:** find and
pin the unseeded RNG path; record the seed in the output.

### B5 — `scripts/46` does not update `meta.rewalked_triggers` · OPEN
It rewrote all 106 rows but left the meta untouched, so the NR-31 stale label still marks our
own freshly-computed numbers as stale. **Fix:** on a per-burst rewalk, append the trigger to

### B6 — `scripts/47_mvt_cwt_crosscheck.py` reads bins from a path that need not exist · OPEN

### B7 — `scripts/48` path inconsistency · FIXED 2026-09-05
Figures resolve relative to `--out`, but the fit table is looked up at `--out/<trig>/…`. There
is no single `--out` that satisfies both, which is why the first assembly reported 7 missing
figures. `spectral_evolution.png` and `ep_kt_correlation.png` were the ONLY figures referenced with a
trigger-nested path, so they always reported missing when `--out` was the burst directory
(which every other figure assumes). **Fix applied:** `_engine_fig()` returns whichever relative
layout exists. The report now resolves **0 missing figures**.

### B8 — the step-8 SED panels cannot produce error bands · OPEN (engine-level)
`CPL+BB` at T_INT: **83.4% of error-propagation samples rejected at the parameter bounds** →
no 68% band at all. `SBPL+BB`: band **suppressed** because the interval excludes its own
best-fit curve over 38% of the range ("railed solution"). Both are honest disclosures on the
figure face, but they mean **no uncertainty band exists for the tie heads of this burst**.
**Fix direction:** this is the rail problem (§D2), not a plotting bug — a spectrum whose β runs
to the floor cannot have a meaningful band.

### B9 — figure-geometry defects should be caught by a test, not by a verifier · OPEN
Five verification rounds were spent on one QC figure. A mechanical check — every label against

### B10 — `_divergence_note` in `scripts/44` matches ledger rows by bare substring · OPEN

### B11 — the display layer reads DIFFERENT bins from the fitting layer · FIXED for this burst, OPEN as a default
**This is why there were no individual per-block fit figures at all.** `scripts/41_nuFnu_panels.py`
takes its bin edges from `BLOCKS_ROOT`, defaulting to **`results/clean_blocks`** — the June-2026
pre-approval blocks — while the fits were run on `results/mine/blocks`, the August post-approval
re-blocking. The edges differ (e.g. bin1 `[23.54, 24.69]` vs the engine's `[23.611, 24.714]`;
bin14 ends 44.60 vs 43.97), the panel looks the engine row up by `(T_START, T_STOP)` rounded to
2 dp, finds nothing, and prints **`FIT FAILED [NO ENGINE ROW]` in every panel** — a silently
empty montage that looks like 15 failed fits rather than a path mismatch.
**Worked around** by exporting `BLOCKS_ROOT=results/mine/blocks` (and `FITS_TABLE`), after which
14/15 panels render with the engine's stored winners, matching `BEST_AIC_MODEL` exactly.
**Fix:** the blocks root must be derived from the fit table's own `blocks_file` metadata (it is
recorded in `spectral_fits.json`), never from an independent default; and a panel that finds no
engine row for EVERY bin should fail loudly, not draw 15 red "FIT FAILED" cells.

### B12 — the panel layer disagrees with the engine on 2 of 16 cells · OPEN
With the correct bins, blocks **0** and **6** carry `[! PANEL!=ENGINE dAIC=+inf]`; block 0 draws
`FIT FAILED` outright. Both are `CPL+BB` winners that the engine records as `STATUS=OK`,
`VALID=True`, with **`MINOS_OK=False`** and `ERROR_METHOD=COVARIANCE_MC` — i.e. exactly the fits
whose errors needed the MC fallback are the ones the display cannot reproduce. Block 0 is also

The standing rule applies (`REVIEW_INDEX_106.md`): *trust the table, not the curve*.
**Fix:** find why the replay diverges for MC-error two-component fits; until then the montage
must state that a `PANEL!=ENGINE` cell is a display failure, not a fit failure.
